# API contract

All requests and responses use JSON. Send `Authorization: Bearer <token>` after login. Errors have `{ "error": "Korean explanation" }` and an appropriate 4xx/5xx status. Money is KRW integer. IDs are integers. Timestamps are UTC ISO strings. Requests that create orders, roll dice, grant Instagram bonuses, or claim rewards require a unique `request_id` string; retries with the same body and ID return the original result. An ID reused for different input returns 409.

## Public and buyer

- `GET /api/health` → `{ok:true,commit?}`. Deployed releases report their exact Git commit; local development omits `commit`.

- `GET /api/config` → `{demo,milestones:[{threshold,kind,name,extra}],dice_types:[{kind,name,color}],staff_password_hint?}`. Dice faces and price bands are server-only. Password hint exists only in local demo.
- `POST /api/auth/register` or `/api/auth/login` body register `{name,phone,pin}`, login `{phone,pin}` → `{token,user}`. PIN remains exactly four numeric digits. Only `010NNNNNNNN` or `010-NNNN-NNNN` is accepted; all other characters/spacing/positions are rejected. DB stores canonical dashed TEXT. Phone is unique; duplicate nicknames are allowed. Phone is omitted from buyer responses and profile changes cannot alter it.
- `POST /api/staff/login` body `{name,password}` → `{token,user}`.
- `GET /api/auth/me` → `{user}`. `POST /api/auth/logout` → `{ok:true}`.
- `POST /api/profile` body `{avatar:{face_shape,skin,expression,glasses,hairpin}}` → `{user}`. Saves the authenticated account's appearance only. Five options are required; unknown fields/values are rejected. Available values: `face_shape=madeleine|financier|pound`, `skin=light|warm|deep`, `expression=smile|happy|wink|surprised`, `glasses=none|round|square|sunglasses`, `hairpin=none|bread_101|…|bread_111`. A bread hairpin requires an approved purchase of the same product in a walk-in, preorder or manual order. Milk, pending/cancelled orders, rewards and Instagram certification do not unlock pins. Unowned pins return 403 without saving any changes. Ownership is read again in the save transaction. Sunglasses require the claimed 15-point milestone; an unearned selection returns 403. Reads also remove unowned equipped sunglasses. Legacy face choices and six-field profiles remain readable; old hair fields are ignored and free star/flower/leaf pins become `none`.
- `GET /api/products` → `{products:[{id,name,subtitle,price,stock,preorder_stock,reward_stock,category,image,unit}]}`.
- `GET /api/orders` → `{orders:[order]}` for current buyer.
- `POST /api/orders` body `{items:[{product_id,quantity}],request_id}` → `{order}`. Reserves walk-in stock immediately.
- `POST /api/guest/orders` (no login) body `{name,items:[{product_id,quantity}],request_id}` → `{order}`. `request_id` must be a cryptographically random UUID or 32-character lowercase hex receipt key; reuse it only for an identical retry. Creates no user/session. Shares the integer order ID sequence and pending → approve/cancel inventory workflow. No dice.
- `GET /api/guest/orders/{id}` requires `Authorization: Bearer <original request_id>` → `{order}` with current status. The UI stores the receipt on that device; an order number alone cannot retrieve it. Receipt keys are stored hashed in the DB and never put in URLs.
- `GET /api/preorders/lookup?name=김소연` → `{reservation:{id,name,items,total,status}}`. Looks up the reservation name using the logged-in account phone internally. Nickname may differ from reservation name. Buyer responses omit phone. Optional phone parameter must exactly normalize to the account phone; otherwise 403.
- `POST /api/preorders/:id/claim` body `{request_id}` → `{order}`. Requires a matching account phone and that buyer's successful reservation lookup within the last 24 hours. Existing claim returns its order, including across retries.
- `POST /api/dice/roll` body `{kind,request_id}` → `{id,dice:{kind,name,color},result,value,score,dice_balance,user,fulfillment}`. The server chooses one of six faces for the owned die. `result=score` adds the returned value; `result=milk` adds zero points and creates an `awaiting_choice` fulfillment. The die is consumed and the outcome is fixed even if both drinks are out of stock. No drink stock is reserved until the buyer selects milk or soymilk. A missing kind uses the first owned type for older clients. Client-supplied result/face/value fields are rejected.
- `POST /api/reward-requests/:id/choose` body `{product_id:112|113,request_id}` → `{request}`. Owner only; checks stock and reserves one chosen drink atomically, moving `awaiting_choice → pending`. Other products return 400; sold out or changing an already chosen drink returns 409. Same chosen product can be retried without another hold.
- `POST /api/reward-requests/:id/decline` body `{request_id}` → `{request}`. Owner can decline an unselected drink; closes the request without stock changes, refunds or redraws. Pending selections require staff cancellation.
- `GET /api/leaderboard` → `{leaders:[entry],neighbors:[entry],me:entry,total_participants}`. `entry={rank,id,name,score,is_me}`. Leaders are top three; neighbors contain self and up to two users on each side.
- `POST /api/rewards/claim` body `{threshold?,request_id}` → `{reward:{id,product_name,product_id,threshold,kind,created_at},user}`. Claims the selected achieved milestone once; without threshold, defaults to the first unclaimed milestone. Claims may be made in any order. Supported milestones: 5 oatmeal, 10 milk, 15 sunglasses, 20 random bread, 30 random bread. No claims beyond 30. Badges/titles are announcements only. Physical rewards create `reward.fulfillment`: bread/oatmeal reserve one unit immediately (`pending`), milk creates an unreserved `awaiting_choice` request. Bread/oatmeal out-of-stock returns 409 without consuming eligibility. The milestone/level is earned on claim and remains after physical cancellation. Digital sunglasses grant immediately without a fulfillment. Bread selection uses `stock² / Σstock²` among remaining walk-in bread stock, excluding drinks/reserved/pending-order/pending-reward units. Sunglasses unlock wearing the profile accessory without inventory use.
- `GET /api/rewards` → `{rewards:[reward],requests:[fulfillment]}`. Each new physical reward links `fulfillment`; historical records and digital grants have no request. Includes new milestone records, `kind=dice_milk` wins (`threshold=0`) and preserved `kind=legacy_bread` records. IDs are local to each kind/table; combine kind and ID for identification.

`user={id,name,role,score,dice_balance,rewards_claimed,level,avatar,profile_customized,unlocked_hairpins,dice,claimed_milestones,sunglasses_unlocked}`. `dice` lists owned `{kind,name,color,quantity}` entries; `claimed_milestones` is the new-plan threshold list and `sunglasses_unlocked` reflects the 15-point claim. A profile is always present: accounts with no saved choices receive a deterministic default and `profile_customized:false`. Leaderboard entries also include `avatar` and `profile_customized`, so all displayed participants have portraits. Staff buyer lists use the same appearance. `unlocked_hairpins` always includes `none`; only the own-account response and staff buyer lists include it. Leaderboard entries do not reveal purchase-derived unlocks. `order={id,type,status,customer_name,user_id,items,total,quantity,dice_quantity,dice:{kind,name,color},created_at,approved_at,cancelled_at}`. Order types: `walkin`, `preorder`, `manual`. Status: `pending`, `approved`, `cancelled`. `items=[{product_id,name,quantity,price}]`.

`reward_stock` in product responses is a deprecated compatibility field fixed at zero after startup migration. Any old separate stock is moved to `stock` once, with inventory logs; staff writes to `reward_stock` are rejected.

The current menu and prices are documented in [docs/MENU.md](../docs/MENU.md). `name` is the actual product/flavor; `subtitle` is the alchemy concept. `unit` is `개` or `세트`. One donut set contains five donuts, costs 2,000 KRW, consumes one inventory unit, and grants one die upon approval.

`fulfillment={id,user_id,milestone_id,roll_id,kind,status,product_id,supply_key,product_name,created_at,requested_at,processed_at}`. Exactly one source ID is present; kind is bread/milk/oatmeal. Status is awaiting_choice/pending/approved/cancelled. Staff responses add customer_name, threshold, processed_by and current remaining_stock. No old grants are automatically enqueued on migration. Drink choice updates the associated milestone product snapshot. Cancellation restores stock but keeps the fixed draw, consumed die and milestone/digital progress.

## Staff

- `POST /api/staff/manual-event-grants` → `{grant,user}`. Staff-only, immediate completion, no purchase/dice/revenue. Requires `request_id` and nonempty `reason` (up to 200 characters). The same request ID/body grants once; conflicting reuse returns 409. Stock/score/audit/idempotency commit atomically.
  - Recipient: `{user_id}` for a registered buyer, or `{guest:true,name}` for a guest. Guest mode creates no account/session and permits physical goods only.
  - Bread: `{kind:"bread",product_id,quantity}`. Select a bread product; deduct shared walk-in stock. Quantity is 1–100 selling units (donuts: sets).
  - Gift: `{kind:"gift",gift:"oatmeal"|"milk"|"soymilk",quantity}` deducts the matching supply/product stock. `{gift:"custom",gift_name,quantity}` records a named physical prize without tracked stock.
  - Profile gift: `{kind:"gift",gift:"sunglasses",quantity:1}` unlocks sunglasses for the selected account without changing score, level or milestone claims. Guests and already-unlocked accounts are rejected.
  - Score: `{kind:"score",points}` adds 1–10,000 points to the selected account and ranking. Normal milestone claiming remains available; rewards are not automatically claimed.
  - `GET /api/staff/dashboard` includes `manual_grants` (latest 300), with integer grant ID, recipient snapshot, item/points, quantity, reason, staff ID/name and timestamp. For an existing pending reward, use normal approval/cancellation first to avoid a second grant.

Dashboard order items additionally include `remaining_stock` and `unit`, including historical menu items. This is the current available `stock` (`preorder_stock` for preorder orders), read in the same transaction as the dashboard. Pending orders have already deducted their quantities; this is not a historical per-order snapshot. Buyer order responses do not include these fields.

- `GET /api/staff/dashboard` → `{orders,products,stats:{revenue,approved_orders,pending_orders,bread_sold,milk_stock,pending_rewards},users,reservations,inventory_logs,events,memos,schedule,rewards,event_supplies,reward_requests}`. Newest orders and logs first. Staff-only account list contains buyer users only. `reservations` includes all reservations, newest first, as `{id,name,phone,status,items,total}`; status is `reserved`, `pending` or `approved`. This contact list is staff-only. Rewards include `customer_name` for handing out event bread.
- `POST /api/staff/reward-requests/:id/approve` or `/cancel` body `{}` → `{request}`. Approval accepts only `pending` and makes the hold final without another deduction. Cancellation accepts pending/awaiting-choice, restores exactly one held product/supply, and is final. Same transition retries are no-ops; reverse transitions return 409. Digital grants are excluded.
- `POST /api/staff/orders/:id/approve` or `/cancel` body `{}` → `{order}`. Repeated identical transition is a no-op; approved orders cannot cancel, cancelled orders cannot approve. Approval grants `dice_quantity` of `order.dice.kind` (walk-in/manual per bread, preorder one price-tier die). Cancellation restores reserved inventory exactly once.
- `POST /api/staff/inventory` body `{product_id,bucket,delta,reason,request_id?}` → `{products,milk_stock}`. Supplying `request_id` makes retries safe and rejects different input with the same ID. Use bucket `stock` (bread sales/rewards or milk sales/dice or milestone rewards) or `preorder_stock`. Milk is product 112. Legacy bucket `milk` remains an alias for product 112 `stock`; product_id is ignored for this alias. Delta must be nonzero integer. Result cannot be negative; unclaimed reservations' allocated bread cannot be removed from `preorder_stock`.
- `POST /api/staff/manual-sale` body `{user_id,items:[{product_id,quantity}],request_id}` → `{order,user}`. Instead of `user_id`, `{guest:true,name}` records an accountless sale (`user:null`, no dice), or `{name,phone,pin}` creates/reuses a buyer account (an existing phone requires its PIN). Immediate approval and inventory decrement. Account-linked bread units grant dice.
- `POST /api/staff/preorders/lookup` body `{name,phone}` → `{reservation:{id,name,phone,items,total,status,dice_quantity,order}}`. Staff-only exact lookup; includes any linked pickup order. This does not grant a buyer's 24-hour claim authorization.
- `POST /api/staff/preorders/:id/complete` body `{name,phone,user_id,request_id}` → `{order,user,reservation,already_completed}`. Immediately completes the matching reservation using its original items/prices and reserved inventory. For an unclaimed reservation, staff may select any existing buyer `user_id`, including one whose account name differs from the reservation; the original reservation name/phone is preserved and the order/dice are added to that account. Instead of `user_id`, provide `pin` to create the buyer account under the reservation name; an existing account under that reservation phone requires its matching PIN. Staff buyer lists include canonical phone to distinguish duplicate nicknames. An existing pickup request is approved without another inventory deduction. Repeated completion returns the same order without additional dice or stock changes. A linked order keeps its existing buyer and a different `user_id` is rejected. Account creation, stock, order, reservation and dice commit together.
  - `{guest:true}` instead of `user_id`/`pin` fulfills an unclaimed reservation under its reservation name without an account or dice. Name and phone still verify the reservation. An already account-linked request cannot be converted to a guest order.
- `POST /api/staff/event-supplies` body `{key:"oatmeal",delta,reason,request_id}` → `{supply:{key,name,stock}}`. Staff-only signed adjustment with a nonnegative stock guarantee and inventory log. Oatmeal is reward-only, not a sales product.
- `POST /api/staff/instagram` body `{user_id,request_id}` → `{event,user,milk_stock}`. One certification per registered buyer, always grants one `instagram` die. Does not check or deduct milk. New events retain compatibility columns `milk_quantity=0,dice=1`; old records are preserved. Old requests asking for milk or a different dice quantity return 400.
- `POST /api/staff/memos` body `{content}` → `{memo}`.
- `POST /api/staff/preorders/import` body `{reservations:[{name,phone,items:[{product_id,quantity}]}]}` → `{imported:number}`. Atomic whole batch. A reservation's bread moves from walk-in `stock` into reserved `preorder_stock`. Duplicate name/phone is rejected.

Inventory log: `{id,product_id,product_name,bucket,delta,reason,actor,created_at}`. Event: `{id,user_id,customer_name,type,milk_quantity,dice,created_at}`. Memo: `{id,content,author,created_at}`. Schedule: `{id,name,time,role}`.

Demo buyer: `010-1234-5678 / 1234` (nickname 김소연, DEMO_SEED=1 only), preorder telephone `01012345678`. Staff: any name and configured `STAFF_PASSWORD` (local default `butter2026`).

Products include `dice_per_unit` (1 for bread, 0 for both drinks) and `reward_eligible` (false for both drinks). `order.quantity` counts all purchased units; `order.dice_quantity` counts walk-in/manual bread units or one die per bread-containing preorder. Preorder color depends on the reservation total (original prices, including drinks). Drink-only orders grant zero dice. Milk (112) and soymilk (113) each cost 1,000 KRW and are excluded from random bread rewards. Products expose beverage_reward_eligible for drink choice. `stats.milk_stock` is a compatibility view of product 112 stock; `stats.bread_sold` excludes both drinks. Existing `settings.milk_stock` moves into product 112 once on startup and is then kept at zero.
