# API contract

All requests and responses use JSON. Send `Authorization: Bearer <token>` after login. Errors have `{ "error": "Korean explanation" }` and an appropriate 4xx/5xx status. Money is KRW integer. IDs are integers. Timestamps are UTC ISO strings. Requests that create orders, roll dice, grant Instagram bonuses, or claim rewards require a unique `request_id` string; retries with the same body and ID return the original result. An ID reused for different input returns 409.

## Public and buyer

- `GET /api/health` → `{ok:true,commit?}`. Deployed releases report their exact Git commit; local development omits `commit`.

- `GET /api/config` → `{demo,milestones:[{threshold,kind,name,extra}],dice_types:[{kind,name,color}],staff_password_hint?}`. Dice faces and price bands are server-only. Password hint exists only in local demo.
- `POST /api/auth/register` or `/api/auth/login` body register `{name,phone,pin}`, login `{phone,pin}` → `{token,user}`. PIN remains exactly four numeric digits. Only `010NNNNNNNN` or `010-NNNN-NNNN` is accepted; all other characters/spacing/positions are rejected. DB stores canonical dashed TEXT. Phone is unique; duplicate nicknames are allowed. Phone is omitted from public user/profile/leaderboard data and profile changes cannot alter it. The authenticated buyer alone receives their own phone as a pickup form default.
- `POST /api/staff/login` body `{name,password}` → `{token,user}`.
- `GET /api/auth/me` → `{user,pickup_defaults:{name,phone}}` for the current buyer; staff receive only `{user}`. Defaults are private to that authenticated account and do not change its nickname/phone. `POST /api/auth/logout` → `{ok:true}`.
- `POST /api/profile` body `{avatar:{face_shape,skin,expression,glasses,hairpin},badge_id?,title_id?}` → `{user}`. Saves the authenticated account's appearance and optional owned badge/title selections in one transaction. Five options are required; unknown fields/values are rejected. Available values: `face_shape=madeleine|financier|pound`, `skin=light|warm|deep`, `expression=smile|happy|wink|surprised`, `glasses=none|round|square|sunglasses`, `hairpin=none|bread_101|…|bread_111`. A bread hairpin requires an approved purchase of the same product in a walk-in, preorder or manual order. Milk, pending/cancelled orders, rewards and Instagram certification do not unlock pins. Unowned pins return 403 without saving any changes. Ownership is read again in the save transaction. Sunglasses require the claimed 15-point milestone or a staff sunglasses grant; an unearned selection returns 403. Reads also remove unowned equipped sunglasses. Legacy face choices and six-field profiles remain readable; old hair fields are ignored and free star/flower/leaf pins become `none`.
- `GET /api/products` → `{products:[{id,name,subtitle,price,stock,preorder_stock,reward_stock,category,image,photo,unit}]}`.
- `GET /api/orders` → `{orders:[order]}` for current buyer.
- `POST /api/orders` body `{items:[{product_id,quantity}],request_id}` → `{order}`. Reserves walk-in stock immediately.
- `POST /api/guest/orders` (no login) body `{name,items:[{product_id,quantity}],request_id}` → `{order}`. `request_id` must be a cryptographically random UUID or 32-character lowercase hex receipt key; reuse it only for an identical retry. Creates no user/session. Shares the integer order ID sequence and pending → approve/cancel inventory workflow. No dice.
- `GET /api/guest/orders/{id}` requires `Authorization: Bearer <original request_id>` → `{order}` with current status. The UI stores the receipt on that device; an order number alone cannot retrieve it. Receipt keys are stored hashed in the DB and never put in URLs.
- `GET /api/preorders/lookup?name=예약자&phone=01012345678` → `{reservation:{id,name,items,total,status}}`. Looks up the exact submitted name and normalized phone, which may differ from the logged-in account. Omitted values default to that account nickname/phone. Account fields are unchanged. Buyer reservation responses omit phone.
- `POST /api/preorders/:id/claim` body `{request_id}` → `{order}`. Requires that buyer's successful name/phone lookup of this reservation within the last 24 hours. The requesting account receives the order and dice after normal staff approval. A reservation already linked to a different account is rejected; an existing same-account claim returns its order across retries.
- `POST /api/dice/roll` body `{kind,request_id}` → `{id,dice:{kind,name,color},result,value,score,dice_balance,user,fulfillment}`. The server chooses one of six faces for the owned die. `result=score` adds the returned value; `result=milk` adds zero points and creates an `awaiting_choice` fulfillment. The die is consumed and the outcome is fixed even if both drinks are out of stock. No drink stock is reserved until the buyer selects milk or soymilk. A missing kind uses the first owned type for older clients. Client-supplied result/face/value fields are rejected.
- `POST /api/reward-requests/:id/choose` body `{product_id:112|113,request_id}` → `{request}`. Owner only; checks sale stock and the chosen drink's event limit in the same transaction, moving `awaiting_choice → pending`. Exhausted limits return 409 and keep the choice open. Same chosen product can be retried without another hold.
- `POST /api/reward-requests/:id/decline` body `{request_id}` → `{request}`. Owner can decline an unselected drink; closes the request without stock changes, refunds or redraws. Pending selections require staff cancellation. The buyer can always use `취소하기` before choosing a drink, including when only milk is sold out. This calls `/decline`, moves the request to `cancelled` and removes it from the staff `음료 선택 중` queue. `나중에 선택하기` only closes the dialog and deliberately keeps the request open. A successful mutation updates both the active request and reward-history copy immediately, even if the following refresh fails.
- `GET /api/leaderboard` → `{leaders:[entry],neighbors:[entry],me:entry,total_participants}`. `entry={rank,id,name,score,level,avatar,profile_customized,equipped_badge,equipped_title,is_me}`. `level=min(5,rewards_claimed)` matches the account and current achievement-notice profile; raw claim counts remain private. Leaders are top three; neighbors contain self and up to two users on each side.
- `POST /api/rewards/claim` body `{threshold?,request_id}` → `{reward:{id,product_name,product_id,threshold,kind,created_at},user}`. Claims the selected achieved milestone once; without threshold, defaults to the first unclaimed milestone. Claims may be made in any order. Supported milestones: 5 oatmeal, 10 milk, 15 sunglasses, 20 random bread, 30 random bread. No claims beyond 30. Badges/titles are announcements only. Physical rewards create `reward.fulfillment`: bread/oatmeal reserve one unit immediately (`pending`), milk creates an unreserved `awaiting_choice` request. Bread/oatmeal out-of-stock returns 409 without consuming eligibility. The milestone/level is earned on claim and remains after physical cancellation. Digital sunglasses grant immediately without a fulfillment. Bread selection uses `stock² / Σstock²` among remaining walk-in bread stock, excluding drinks/reserved/pending-order/pending-reward units. Sunglasses unlock wearing the profile accessory without inventory use.
- `GET /api/rewards` → `{rewards:[reward],requests:[fulfillment]}`. Each new physical reward links `fulfillment`; historical records and digital grants have no request. Includes new milestone records, `kind=dice_milk` wins (`threshold=0`) and preserved `kind=legacy_bread` records. IDs are local to each kind/table; combine kind and ID for identification.

`user={id,name,role,score,dice_balance,rewards_claimed,level,avatar,profile_customized,unlocked_hairpins,dice,claimed_milestones,sunglasses_unlocked}`. `dice` lists owned `{kind,name,color,quantity}` entries; `claimed_milestones` is the new-plan threshold list and `sunglasses_unlocked` reflects the 15-point claim. A profile is always present: accounts with no saved choices receive a deterministic default and `profile_customized:false`. Leaderboard entries also include `avatar` and `profile_customized`, so all displayed participants have portraits. Staff buyer lists use the same appearance. `unlocked_hairpins` always includes `none`; only the own-account response and staff buyer lists include it. Leaderboard entries do not reveal purchase-derived unlocks. `order={id,type,status,customer_name,user_id,items,total,quantity,dice_quantity,dice:{kind,name,color},created_at,approved_at,cancelled_at}`. Order types: `walkin`, `preorder`, `manual`. Status: `pending`, `approved`, `cancelled`. `items=[{product_id,name,quantity,price}]`.

`reward_stock` in product responses is a deprecated compatibility field fixed at zero after startup migration. Any old separate stock is moved to `stock` once, with inventory logs; staff writes to `reward_stock` are rejected.

The current menu and prices are documented in [docs/MENU.md](../docs/MENU.md). `name` is the actual product/flavor; `subtitle` is the alchemy concept. `unit` is `개` or `세트`. One donut set contains five donuts, costs 2,000 KRW, consumes one inventory unit, and grants one die upon approval.

`fulfillment={id,user_id,milestone_id,roll_id,kind,status,product_id,supply_key,product_name,created_at,requested_at,processed_at}`. Exactly one source ID is present; kind is bread/milk/oatmeal. Status is awaiting_choice/pending/approved/cancelled. Staff responses add customer_name, threshold, processed_by and current remaining_stock. No old grants are automatically enqueued on migration. Drink choice updates the associated milestone product snapshot. Cancellation restores stock but keeps the fixed draw, consumed die and milestone/digital progress.

## Staff

- `POST /api/staff/manual-event-grants` → `{grant,user}`. Staff-only, immediate completion, no purchase/dice/revenue. Requires `request_id` and nonempty `reason` (up to 200 characters). The same request ID/body grants once; conflicting reuse returns 409. Stock/score/audit/idempotency commit atomically.
  - Recipient: `{user_id}` for a registered buyer, or `{guest:true,name}` for a guest. Guest mode creates no account/session and permits physical goods only.
  - Bread: `{kind:"bread",product_id,quantity}`. Select a bread product; deduct shared walk-in stock. Quantity is 1–100 selling units (donuts: sets).
  - Gift: `{kind:"gift",gift:"oatmeal"|"milk"|"soymilk",quantity}` deducts the matching supply/product stock. `{gift:"custom",gift_name,quantity}` records a named physical prize without tracked stock.
  - Profile gift: `{kind:"gift",gift:"sunglasses",quantity:1}` unlocks sunglasses for the selected account without changing score, level or milestone claims. Guests and already-unlocked accounts are rejected.
  - Score: `{kind:"score",points}` adds 1–10,000 points to the selected account and ranking. Normal milestone claiming remains available; rewards are not automatically claimed.
  - `GET /api/staff/dashboard` includes `manual_grants` (latest 300), with integer grant ID, recipient snapshot, item/points, quantity, reason, staff ID/name and timestamp. For an existing pending reward, use normal approval/cancellation first to avoid a second grant.

Dashboard order items additionally include `remaining_stock` and `unit`, including historical menu items. This is the current available `stock` (`preorder_stock` for preorder orders), read in the same transaction as the dashboard. Pending orders have already deducted their quantities; this is not a historical per-order snapshot. Buyer order responses do not include these fields.

- `GET /api/staff/dashboard` → `{orders,products,stats:{revenue,approved_orders,pending_orders,bread_sold,milk_stock,pending_rewards},users,reservations,inventory_logs,events,memos,schedule,rewards,event_supplies,reward_requests}`. Newest orders and logs first. Staff-only account list contains buyer users only. `reservations` includes all reservations, newest first, as `{id,name,phone,status,items,total}`; status is `reserved`, `pending` or `approved`. This contact list is staff-only. Rewards include `customer_name` for handing out event bread.
- `POST /api/staff/reward-requests/:id/approve` or `/cancel` body `{}` → `{request}`. Approval accepts only `pending` and makes the hold final without another deduction. Cancellation accepts pending/awaiting-choice, restores exactly one held product/supply, and is final. Same transition retries are no-ops; reverse transitions return 409. Digital grants are excluded.
- `POST /api/staff/orders/:id/approve` or `/cancel` body `{}` → `{order}`. Repeated identical transition is a no-op; approved orders cannot cancel, cancelled orders cannot approve. Approval grants `dice_quantity` of `order.dice.kind` (walk-in/manual per bread, preorder one price-tier die). Cancellation restores reserved inventory exactly once.
- `POST /api/staff/inventory` body `{product_id,bucket,delta,reason,request_id?}` → `{products,milk_stock}`. Supplying `request_id` makes retries safe and rejects different input with the same ID. Use bucket `stock` (bread/drink sales and event rewards). Milk is product 112. Legacy bucket `milk` remains an alias for product 112 `stock`; product_id is ignored for this alias. Delta must be nonzero integer and the result cannot be negative. Manual `preorder_stock` adjustments, positive or negative, return 400; preorder inventory changes only through reservation registration, pickup requests, completion and cancellation.
- `POST /api/staff/manual-sale` body `{user_id,items:[{product_id,quantity}],request_id}` → `{order,user}`. Instead of `user_id`, `{guest:true,name}` records an accountless sale (`user:null`, no dice), or `{name,phone,pin}` creates/reuses a buyer account (an existing phone requires its PIN). Immediate approval and inventory decrement. Account-linked bread units grant dice.
- `POST /api/staff/preorders/lookup` body `{name,phone}` → `{reservation:{id,name,phone,items,total,status,dice_quantity,order}}`. Staff-only exact lookup; includes any linked pickup order. This does not grant a buyer's 24-hour claim authorization.
- `POST /api/staff/preorders/:id/complete` body `{name,phone,user_id,request_id}` → `{order,user,reservation,already_completed}`. Immediately completes the matching reservation using its original items/prices and reserved inventory. For an unclaimed reservation, staff may select any existing buyer `user_id`, including one whose account name differs from the reservation; the original reservation name/phone is preserved and the order/dice are added to that account. Instead of `user_id`, provide `pin` to create the buyer account under the reservation name; an existing account under that reservation phone requires its matching PIN. Staff buyer lists include canonical phone to distinguish duplicate nicknames. An existing pickup request is approved without another inventory deduction. Repeated completion returns the same order without additional dice or stock changes. A linked order keeps its existing buyer and a different `user_id` is rejected. Account creation, stock, order, reservation and dice commit together.
  - `{guest:true}` instead of `user_id`/`pin` fulfills an unclaimed reservation under its reservation name without an account or dice. Name and phone still verify the reservation. An already account-linked request cannot be converted to a guest order.
- `POST /api/staff/event-supplies` body `{key:"oatmeal",delta,reason,request_id}` → `{supply:{key,name,stock}}`. Staff-only signed adjustment with a nonnegative stock guarantee and inventory log. Oatmeal is reward-only, not a sales product.
- Dashboard `event_supplies` rows include `{key,name,stock,held,delivered}`. `stock` is available physical stock. `delivered` includes approved rewards, manual grants, and historical direct awards.
- `POST /api/staff/event-beverage-limits` body `{product_id:112|113,limit,request_id}` → `{beverage:{product_id,name,limit,held,delivered,remaining}}`. Sets one drink's cumulative event limit (initially 0). The staff dashboard includes both rows in `event_beverage_limits`. Pending choices and delivered drinks, including manual grants and historical direct awards, count toward the limit. Cancellation releases the hold. A limit below already held and delivered quantities returns 409. Public drink products expose `event_reward_remaining`; purchases use sale stock independently.
- Inventory sales totals use all approved order lines, including preorders and manual sales. `stats.bread_sold` and `stats.bread_revenue` exclude both drinks. Revenue uses the prices recorded at purchase. `stats.milk_sold` and `stats.soymilk_sold` count each drink separately. `stats.bread_stock_total` adds current bread stock, preorder stock and units held for pending orders or rewards. `stats.bread_event_given` counts approved event bread, immediate manual bread grants and historical direct bread awards. A donut set counts as one unit.
- `POST /api/staff/instagram` body `{user_id,request_id}` → `{event,user,milk_stock}`. One certification per registered buyer, always grants one `instagram` die. Does not check or deduct milk. New events retain compatibility columns `milk_quantity=0,dice=1`; old records are preserved. Old requests asking for milk or a different dice quantity return 400.
- `POST /api/staff/memos` body `{content}` → `{memo}`.
- `POST /api/staff/preorders/import` body `{reservations:[{name,phone,items:[{product_id,quantity}]}]}` → `{imported:number}`. Atomic whole batch. A reservation's bread moves from walk-in `stock` into reserved `preorder_stock`. Duplicate name/phone is rejected.

Inventory log: `{id,product_id,product_name,bucket,delta,reason,actor,created_at}`. Event: `{id,user_id,customer_name,type,milk_quantity,dice,created_at}`. Memo: `{id,content,author,created_at}`. Schedule: `{id,name,time,role}`.

Demo buyer: `010-1234-5678 / 1234` (nickname 김소연, DEMO_SEED=1 only), preorder telephone `01012345678`. Staff: any name and configured `STAFF_PASSWORD` (local default `butter2026`).

Products include `dice_per_unit` (1 for bread, 0 for both drinks) and `reward_eligible` (false for both drinks). `order.quantity` counts all purchased units; `order.dice_quantity` counts walk-in/manual bread units or one die per bread-containing preorder. Preorder color depends on the reservation total (original prices, including drinks). Drink-only orders grant zero dice. Milk (112) and soymilk (113) each cost 1,000 KRW and are excluded from random bread rewards. Products expose beverage_reward_eligible for drink choice. `stats.milk_stock` is a compatibility view of product 112 stock; `stats.bread_sold` excludes both drinks. Existing `settings.milk_stock` moves into product 112 once on startup and is then kept at zero.


## Badges (local changes)

- Buyer/staff user responses include `badges:[{id,name,description,icon,rule,threshold,owned,earned_at}]` for that account. Public leaderboard entries expose only `equipped_badge:{id,name,icon}|null`, never the ownership list or award audit.
- `POST /api/profile` accepts `{avatar,badge_id}`. Use a currently owned badge ID or `null` to remove it. An unearned badge returns 403 and neither appearance nor badge selection changes. Legacy `{avatar}` requests preserve the existing selection.
- Successful 5/10 point reward claims award `score_5` / `score_10` within the same transaction. Failed physical reward claims do not award badges. Existing successful milestone claims are backfilled at startup, once per user/badge, preserving original claim times. No badge is equipped automatically.
- Staff-only `POST /api/staff/badges` body `{name,description,icon,request_id}` → `{badge}` creates a manual-condition definition. Name: 1–40 chars; description/earning hint: 1–240 chars; icon: spark/flask/star/heart/bread/trophy. New definitions appear as locked slots for all accounts.
- Staff-only `POST /api/staff/badge-grants` body `{user_id,badge_id,reason,request_id}` → `{grant,user}`. Registered buyers only; a duplicate ownership returns 409. Same-key identical retries return the original result without awarding again. Grant audit stores staff, reason and timestamp without changing inventory, sales, score, dice or milestone claims.
- Staff dashboard adds `badges` (definitions), `badge_grants` (manual award audit), and per-user badge ownership in `users[].badges`.


## Titles and purchase achievements (local changes)

- Account user responses include `titles:[{id,name,description,style,rule,threshold,owned,earned_at}]` and five private `achievements:[{id,name,description,current,target,unit,completed,badge_id,title,style?,items?,dates?}]` cards. `items` holds that account's approved purchase quantities only. Public leaderboard entries expose `equipped_title:{id,name,style}|null`, never purchase progress, title ownership or phone.
- `POST /api/profile` accepts optional `title_id` alongside `avatar` and optional `badge_id`. Owned ID equips, `null` removes, omitted preserves. Unearned/unknown title returns 403 and the whole profile save rolls back.
- Successful 15/30-point claims grant `score_15` (멋쟁이 마법사) / `score_30` (대현자 연금술사). Purchase approval grants achievement badges and titles atomically. Bread counts aggregate approved preorder, walk-in and manual orders, excluding drinks, free grants and rewards. Four financier variants earn 원소 수집가; all eleven breads earn gold 캄딜 VVIP; five of a bread earn that product's 몰입가 title and the shared focus badge.
- Earliest ten distinct reservation phone numbers by `created_at,id` earn after pickup approval. Import the original applications in chronological order. Daily walk-in/manual first noncancelled bread order by `created_at,id` earns after approval; an earlier pending order blocks later approvals until resolved. KST dates, guest purchases occupy the first slot, one exclusive winner per date. Both first-arrival challenges grant the same lightning badge/title once; daily achievements keep individual dates.
- First title is auto-equipped; new gold titles replace non-gold and VVIP takes priority. No repeat claim/startup overwrites an existing profile selection. Badge selection remains manual. Earned awards are durable; no sale inventory is changed by digital awards.
- Staff-only `POST /api/staff/titles` body `{name,description,style,request_id}` → `{title}`. Name 1–40, hint 1–240 chars, style `magic|gold|lightning`. `POST /api/staff/title-grants` body `{user_id,title_id,reason,request_id}` → `{grant,user}`. Registered buyer only, reason 1–200, duplicate 409, identical request retries return the original response. Staff dashboard adds `titles`, `title_grants` and `users[].titles`.
- Existing badge definitions and ownership migrate to accept `achievement` sources; `user_badges.achievement_id` references `user_achievements`. Existing profiles, badge choices, grants, IDs and timestamps survive. Startup backfills approved purchase achievements and 15/30 point claim titles. No DB reset is needed.


## Staff schedule

`GET /api/staff/dashboard` includes `schedule:[{id,name,time,role,event_date}]` for authenticated staff only. `event_date` is YYYY-MM-DD or null for legacy common shifts; `name` can list several assignees, `time` is 오픈 or HH:MM-HH:MM, and an empty role is permitted. The admin notes tab builds date columns and time rows from these records; no actual roster is bundled with static files. Schedule data is maintained directly in the server DB using `server.schedule.replace_dates` under the write lock. The importer validates the complete payload before replacing only the supplied dates, preserving other dates and common rows. No public schedule or write endpoint is added.


Product `photo` is a local static illustration/photo path. The eleven bread products use distinct WebP artwork under `/assets/products/`; drink products keep the neutral placeholder until artwork is provided. Buyer menu and staff manual-sale/pickup views share the same renderer. This metadata does not change product prices, stock or dice quantities.


## Shared event notices

- Public `GET /api/event-notices` → `{notices:[{id,kind,content,created_at,author}]}`. Newest ID first, at most two, identical for every viewer. Achievement `author` exposes public ID/nickname, current `level`, avatar, equipped badge/title and profile status. Existing notices use the author's current level at read time, including after reward claims. No phone, ownership list, raw claim counts or staff identity. Announcements use a fixed shared `관리자` persona.
- Staff dashboard adds the same `event_notices` list.
- Staff-only `POST /api/staff/event-notices` body `{content,request_id}` → `{notice}`. Trimmed content must be 1–160 characters. No custom author fields. Idempotent retries never recreate a deleted/evicted notice.
- Staff-only `POST /api/staff/event-notices/:id/delete` body `{}` → `{ok:true}`. Repeated deletion succeeds; older notices never resurface.
- New achievement awards publish once in the approval transaction. Creation prunes older rows in the same global write lock, retaining at most two rows across achievements and announcements combined. Startup backfills do not broadcast historical achievements. Clearing the board never erases achievement ownership.


## Fixed administrator profile

- Staff login and `/api/auth/me` return `profile_kind:"admin"`, `avatar:null`, no equipped badge/title and `profile_customized:false`. The client renders the fixed local `assets/admin-avatar-v1.svg`; previously saved staff appearance does not affect it. Buyer customization is unchanged.
- `POST /api/profile` is buyer-only. Staff requests return 403 (`관리자는 공용 프로필을 사용합니다.`) without changing stored choices.
- Shared announcement authors also use `profile_kind:"admin"`, with the generic name `관리자` instead of the staff operator's identity.
