# 구성과 재고 규칙

## 실행 구성

구매자 화면과 담당자 화면은 빌드 과정이 없는 정적 프론트엔드입니다. 로컬에서는 Python HTTP 서버가 정적 파일과 `/api/*`를 함께 제공합니다. API는 로그인 세션, 주문, 예판, 주사위, 순위와 운영 데이터를 처리합니다.

기본 DB는 SQLite이며 `DB_PATH`에 파일을 저장합니다. `DATABASE_URL`이 있으면 psycopg를 통해 PostgreSQL에 연결합니다. 프론트엔드는 같은 API 계약을 사용하므로 나중에 Cloudflare Pages로 분리해도 구매 흐름을 그대로 유지할 수 있습니다.

```text
모바일 구매 화면 ─┐
                  ├─ HTTP JSON API ─ 트랜잭션 ─ SQLite / PostgreSQL
노트북 담당 화면 ─┘
```

## 데이터 역할

| 데이터 | 역할 |
| --- | --- |
| 구매자·세션 | 고유 이름, PIN 인증 정보, 역할, 점수, 남은 주사위, 보상 수령 수 |
| 빵 | 이름·가격·설명 및 현판·이벤트 공용 재고 / 별도 예판 재고 |
| 예판 | 이름+전화번호 기준 예약 항목, 수령 요청과 상태 |
| 예판 조회 확인 | 본인 이름과 전화번호로 조회한 예약에 대한 24시간 수령 요청 권한 |
| 주문·항목 | 현판·예판·수기 유형, 대기·승인·취소 상태, 주문 시점 가격과 수량 |
| 재고 이력 | 어떤 재고가 얼마 바뀌었고 누가 어떤 이유로 수정했는지 |
| 이벤트·보상 | 인스타 지급 이력, 이벤트 빵과 달성 점수 기준 |
| 운영 정보 | 인수인계 메모와 담당자 시간표 |
| 요청 재시도 기록 | 같은 작업 요청의 중복 실행 방지 |

구매자의 전화번호는 예판 확인에 사용됩니다. 외부 운영 시 접근 권한, 보관 기간, 삭제 방법을 행사 운영 기준에 맞게 정해야 합니다. 담당자 화면과 DB 백업에는 개인정보가 포함될 수 있습니다.

## 주문과 재고

현판과 이벤트는 `stock`을 함께 사용합니다. 예판의 `preorder_stock`과 승인 전 주문을 위해 이미 확보한 수량은 추첨하지 않습니다. 이벤트가 당첨되면 현판 재고에서 즉시 1단위를 차감합니다.

| 작업 | 현판·이벤트 공용 | 예판 | 주사위 |
| --- | --- | --- | --- |
| 현판 주문 요청 | 수량 차감 | — | — |
| 현판 승인 | 추가 차감 없음 | — | 빵 수량만 지급 |
| 현판 취소 | 수량 반환 | — | 지급 없음 |
| 예판 사전 등록 | 수량 차감 | 수량 추가 | — |
| 예판 수령 요청 | — | 수량 차감 | — |
| 예판 수령 승인 | — | 추가 차감 없음 | 금액 등급의 예판 주사위 1개 |
| 예판 수령 취소 | — | 수량 반환 | 지급 없음 |
| 수기 현장 판매 | 수량 차감 | — | 즉시 빵 수량만 지급 |
| 수기 예약 수령 | — | 수량 차감 (기존 접수 주문은 추가 차감 없음) | 즉시 예판 주사위 1개 |
| 점수 보상 수령 | 5점 오트밀 / 10점 우유 / 20·30점 빵 차감 | — | — |
| 인스타 이벤트 | — | — | 전용 주사위 1개 |

기존 DB의 별도 `reward_stock`은 앱 시작 시 같은 쓰기 트랜잭션 안에서 현판으로 합치고 0으로 닫습니다. 이전 재고의 합계를 보존하며 이전 이벤트 차감·현판 추가 이력을 남깁니다. 이후 재시작해도 중복해서 합치지 않습니다. 이 컬럼은 기존 DB와 화면의 호환을 위해 남아 있지만 별도 수정은 받지 않습니다.

주문은 `pending → approved` 또는 `pending → cancelled`로만 전환합니다. 같은 승인이나 취소를 다시 눌러도 재고·주사위를 두 번 반영하지 않습니다. 승인 후 취소, 취소 후 승인은 거부합니다.

예판 사전 등록은 현판 재고를 예판 재고로 옮깁니다. 따라서 사전에 예판 수량을 고려한 전체 재고를 먼저 넣고 예판을 등록해야 합니다. 예판 등록은 예약 묶음 전체를 하나의 트랜잭션으로 처리하므로 중복 예약이나 재고 부족이 있으면 일부만 반영되지 않습니다.

예판 수령 요청은 로그인한 본인의 이름과 전화번호로 예약을 먼저 조회해야 가능합니다. 조회 확인은 24시간 유효합니다. 예약 번호만 알아내어 직접 API를 호출하는 방법으로 전화번호 확인을 건너뛸 수 없습니다.

담당자는 별도의 수기 예약 조회 API로 이름·전화번호를 확인한 뒤 수령을 즉시 승인할 수 있습니다. 미접수 예약은 예약 당시 항목과 가격으로 승인 주문을 만들고, 접수된 예약은 기존 주문을 승인합니다. 필요한 구매자 계정 생성, 예판 재고 차감, 예약·주문 상태 변경, 금액 등급의 예판 주사위 1개 지급을 하나의 쓰기 트랜잭션으로 처리합니다. 이미 완료된 예약의 재요청과 구매자·담당자의 동시 처리도 같은 주문으로 귀결됩니다. 담당자 조회는 구매자의 24시간 조회 권한을 만들지 않습니다.

미접수 예약은 담당자가 이름이 다른 기존 구매자 계정에도 연결할 수 있습니다. 원래 예약자 이름·전화번호는 보존하며 주문과 주사위만 선택한 계정에 추가합니다. 접수·완료된 예약의 계정 변경은 거부하므로 동시 처리에서도 한 계정에만 지급합니다. 구매자 본인 조회·수령 API의 이름 및 소유권 검사는 유지합니다. 담당자 대시보드는 모든 예판과 항목을 두 번의 일괄 조회로 가져와 수령 현황을 제공하며, 이 이름·전화번호 목록은 담당자에게만 반환합니다.

## 동시성 및 재시도

재고 확인·차감, 주문 상태 변경·주사위 지급, 점수·보상 처리에는 DB 트랜잭션을 사용합니다. SQLite는 `BEGIN IMMEDIATE`, PostgreSQL은 공통 `pg_advisory_xact_lock(731042026)`으로 쓰기 트랜잭션을 직렬화합니다. 작은 행사 규모에 맞춰 처리량보다 단순한 재고 정합성을 우선했습니다. 마지막 한 개를 두 사람이 동시에 주문해도 성공한 요청 한 개만 재고를 얻어야 합니다.

주문 생성·주사위·수기 판매·인스타 지급·보상 수령은 `request_id`를 사용합니다. 네트워크 오류 후 같은 내용과 같은 ID로 재시도하면 원래 응답을 돌려줍니다. 같은 ID에 다른 내용을 보내면 충돌로 거부합니다. 담당자의 승인·취소는 주문 상태 자체로 중복 처리를 막습니다.

브라우저 갱신은 알림을 가져오는 수단이며 재고의 기준은 항상 DB입니다. 화면에 재고가 남아 보여도 실제 주문 시점에 다른 주문이 먼저 선점하면 재고 부족 응답을 받습니다.

## 이벤트

현판은 승인 빵 1단위당 주사위 1개, 예판은 예약 총액 등급의 주사위 1개, 인스타 인증은 전용 주사위 1개를 지급합니다. `dice_wallet`에 종류별 수량을 저장하고 `dice_balance`는 합계를 유지합니다. 서버가 종류에 맞는 6면 중 하나를 골라 숫자는 점수, 우유 면은 구매자가 우유·두유 중 고를 수 있는 물품 요청을 생성합니다. 면 구성은 프론트/API 메타데이터에 포함하지 않습니다. 상세 운영 규칙은 [담당자 인수인계](STAFF_HANDOVER.md)에 있습니다.

점수 보상은 5점 오트밀, 10점 우유 또는 두유, 15점 선글라스, 20·30점 랜덤 빵을 각 1회 지급합니다. `milestone_claims`에서 선택한 달성 기준을 한 번씩 처리하며 캐릭터는 수령 시 성장합니다. 배지·칭호는 화면 예고만 있습니다. 30점 이후에는 추가 점수 보상 없이 점수·순위가 누적됩니다.

랜덤 빵은 현재 판매 가능한 현판 `stock² / Σstock²`로 추첨합니다. 예판·접수 확보 수량과 우유는 제외하며 도넛은 5개 한 세트가 1단위입니다. 추첨·물품 차감·지급 기록·레벨 변경은 판매와 같은 쓰기 잠금으로 묶습니다. 빵·오트밀 품절이면 보상 신청을 롤백합니다. 우유 면의 굴림은 재고와 무관하게 확정하고 선택권을 남깁니다. 음료 선택 시 품절을 검사하며, 모두 없으면 미수령 또는 나중 선택이 가능합니다. 오트밀은 판매 상품과 분리한 `event_supplies`에서 관리합니다.

기존 계정·점수·주문·재고·굴림·당첨 기록은 그대로 남깁니다. 남은 기존 주사위만 최초 시작 시 `walkin` 지갑으로 한 번 이관합니다. 이전 빵 보상은 새 점수 단계와 분리한 이력으로 표시합니다.

API의 실제 경로와 JSON 예시는 [server/API.md](../server/API.md)를 참고하세요.

## 우유와 인스타 인증

우유(112번)·두유(113번)는 각각 1,000원인 일반 품목이며 `products.stock`·`preorder_stock`·`inventory_logs`로 빵과 함께 관리합니다. 기존 `settings.milk_stock`의 잔량은 시작 시 제품의 현판 재고에 한 번만 합치고 원본을 0으로 닫습니다. 예전 `bucket=milk` API 요청도 같은 제품 재고로 연결합니다. 판매와 우유 보상은 동일한 DB 쓰기 잠금 안에서 처리하므로 마지막 우유를 동시에 두 곳에 배정하지 않습니다.

주문 `quantity`는 빵과 우유를 모두 포함하고, `dice_quantity`는 현판·수기 현장은 우유 제외 수량, 예판은 빵 포함 예약당 1개입니다. 현판 승인·예판 승인·수기 판매의 모든 경로에서 이 값을 사용합니다. 두 음료는 랜덤 빵 추첨에서도 제외합니다.

인스타 이벤트는 등록된 구매자를 한 번 인증하고 `instagram` 주사위 1개만 지급합니다. 우유 재고는 확인·차감하지 않습니다. 예전 우유 직접 지급/선택 체크 기능은 제거했고, 과거 인증 기록은 보존합니다. 네트워크 재시도는 동일 `request_id`로 결과를 재사용합니다.

## 이벤트 물품 지급

새 물품 당첨은 원본 주사위/점수 보상에 UNIQUE로 연결한 `reward_requests`를 만듭니다. 빵·오트밀은 생성 시 재고 확보 후 pending, 음료는 awaiting_choice에서 구매자의 품목 선택 후 pending입니다. 담당자 승인으로 approved가 되어 차감을 유지하고, 취소는 확보한 재고만 반환하여 cancelled로 끝납니다. 상태 검사·재고 반환은 판매와 같은 쓰기 잠금 안에서 수행합니다. 같은 처리는 한 번만 반영하고 반대 상태로 바꿀 수 없습니다. 취소가 추첨 결과·사용한 주사위·점수 단계를 되돌리지는 않습니다. 디지털 보상과 과거 지급은 대기 목록을 만들지 않습니다.

관리자 메뉴는 주문 → 이벤트 → 수기판매 → 재고관리 → 인수인계이며, 인스타 인증은 이벤트 내부 탭에 둡니다. 재고의 접수 보관에는 대기 판매와 대기 이벤트 물량을 모두 합산합니다.
